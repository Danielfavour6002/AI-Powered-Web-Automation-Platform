## Purpose of This Document

Each section ends with a checklist so you can tick off features as they are completed. Nothing is optional unless explicitly marked that way.

## 01 | Project Overview

### What This Platform Does
The platform is a self-hosted web application that lets consultants and teams record interactions with any cloud web application (Oracle Fusion, PeopleSoft, SAP, Workday, or any URL-based system), replay those recordings automatically, generate interaction scripts using an AI agent by uploading a plain-language test description, and export polished documentation with screenshots and video.

The key design goal is **multi-client reuse**. A test recorded once for Client A can be re-run for Client B simply by switching the active client profile. No code changes. No re-recording.

### Existing Code Context
The two repos (noname / testcase) share the same architecture. `testcase` is the cleaner of the two. The developer should treat `testcase` as the base and incorporate the additional UI work from `noname`.

Key components to preserve and improve:
* `core/`: Contains config, database, models, and security. Keep this structure.
* `engine/`: Contains the recorder, runner, parser, AI agent wrapper, and LLM adapter.
* `fusion/`: Contains login helpers. This will be generalized to support any cloud app.
* `web/`: Is the FastAPI + Jinja2 dashboard. This gets a full UI upgrade.
* `reports/`: Generates the Excel output. This gets screenshot and video output added.

## 02 | Configuration System (No .env Files)

This is the most critical architectural requirement. The platform must behave like Oracle Fusion Cloud's own setup screens or PeopleSoft's configuration pages: everything is configured through the UI and stored in the database.

There are no `.env` files in production. The `.env.example` file in the repo is only kept for first-time local developer setup convenience and must be clearly labelled as such.

### Global Application Settings (Stored in DB table: `app_config`)
These are platform-wide settings managed from a Settings page in the UI:

- [ ] Server host and port are configurable from the UI and persisted in the database
- [ ] Database file path is configurable (defaults to `data/platform.db` relative to working directory, never hardcoded)
- [ ] Output root directory for screenshots, videos, and reports is configurable from the UI
- [ ] Log level (DEBUG / INFO / WARNING / ERROR) is configurable from the UI
- [ ] Theme preference (light / dark / system) is stored per-user in the database
- [ ] Default browser to use (Chromium, Firefox, WebKit) is configurable
- [ ] Default recording timeout (seconds before auto-stop) is configurable
- [ ] Maximum concurrent automation runs is configurable
- [ ] Screenshot quality (1-100) and format (PNG / JPEG) are configurable
- [ ] Video recording resolution and frame rate are configurable
- [ ] Report output format defaults (Excel, PDF, HTML) are configurable

### Client Profiles (Stored in DB table: `clients`)
A client profile holds everything needed to connect to one cloud application instance for one organization. The platform supports an unlimited number of client profiles. Switching between them requires no code changes whatsoever.

- [ ] Each client profile has a unique display name (e.g., "Acme Corp - Fusion PROD")
- [ ] Each profile stores the target application type (Oracle Fusion Cloud, PeopleSoft, SAP, Workday, Custom, or any label the user defines)
- [ ] Each profile stores the base URL of the target application
- [ ] Each profile stores the login username for that environment
- [ ] Each profile stores an optional short code / pod identifier used in report file names
- [ ] Each profile stores the consultant or team member initials used in output folder naming
- [ ] Each profile has an active / inactive toggle so retired environments do not appear in run dropdowns
- [ ] Passwords for each client are stored using the OS keyring (Windows Credential Manager / macOS Keychain / Linux Secret Service) under a key derived from the client profile ID. They are never written to a file or the database.
- [ ] Each profile can store a list of custom wait selectors specific to that application (for slow-loading pages)
- [ ] Each profile can store extra HTTP headers or cookies needed for login (some SSO environments require this)
- [ ] Client profiles can be exported to a JSON file (passwords excluded) and imported on another machine
- [ ] Deleting a client profile prompts for confirmation and shows a count of tests that reference it

> **Note:** The existing `.env.example` lists `FUSION_URL`, `FUSION_USER`, `FUSION_POD`, `CONSULTANT`, `HOST`, `PORT`, `DB_PATH`, `OUTPUT_ROOT`. All of these must move into the configuration UI. The `.env.example` is kept for first-run bootstrap only and must display a warning message telling the developer to migrate to the UI config immediately after first launch.

### AI / LLM Provider Settings (Stored in DB table: `llm_providers`)
The platform supports multiple LLM providers. Each provider entry stores:

- [ ] Provider name (OpenAI, Anthropic, Google Gemini, Azure OpenAI, or custom)
- [ ] API key, stored encrypted in the database using a platform-level encryption key derived from a master password set during first-run setup (see Security section)
- [ ] Model name (e.g. gpt-4o, claude-sonnet-4-20250514, gemini-1.5-pro)
- [ ] Optional base URL override for self-hosted or Azure deployments
- [ ] Max tokens per request
- [ ] Temperature setting
- [ ] Active flag so one provider is the default
- [ ] Test connection button that sends a simple ping and shows success or failure with the error message

## 03 | Security Requirements

Security is not an afterthought here. The platform handles credentials for production enterprise systems and must treat them accordingly.

### Password and Credential Handling
- [ ] No password, API key, or secret token is ever written to a file on disk in plaintext
- [ ] No password, API key, or secret token appears in application logs at any level
- [ ] No password appears in any database column. Passwords live exclusively in the OS keyring.
- [ ] API keys for LLM providers are encrypted in the database using AES-256-GCM with a key derived from a master password via PBKDF2 with at least 600,000 iterations and a random salt
- [ ] The master password is set once during first-run setup and is never stored anywhere, only derived keys are stored
- [ ] If the OS keyring is unavailable (some headless Linux servers), the platform falls back to an encrypted secrets file in the data directory, and clearly warns the user about the reduced security posture
- [ ] All password input fields use `type="password"` and disable browser autofill for credential pages
- [ ] Session tokens for the web UI (if multi-user mode is added later) use cryptographically random values of at least 256 bits

### Input Validation
- [ ] All URL inputs are validated as well-formed HTTPS URLs before being saved or used
- [ ] All file upload inputs validate the file extension and MIME type before processing
- [ ] Uploaded files are saved to a configured upload directory, never in the application source tree
- [ ] File paths supplied by configuration are validated to be within allowed directories (no path traversal)
- [ ] The web UI sanitizes all user-supplied text before rendering to prevent XSS

### Operational Security
- [ ] The application binds to `127.0.0.1` by default. The configuration UI shows a clear warning if the user changes the bind address to `0.0.0.0`.
- [ ] Playwright automation runs in a separate process, not in the same thread as the web server
- [ ] Sensitive configuration pages (client profile editing, LLM key management) are accessible only after the user enters the master password once per session

## 04 | Session Recording

Recording captures every interaction a human performs in a real browser window and saves it as a structured, replayable sequence of steps. This is the foundation of the platform.

### Starting a Recording
- [ ] The dashboard has a clearly visible "New Recording" button on the main navigation
- [ ] Before launching the browser, the user selects a client profile from a dropdown (populated from all active profiles in the database)
- [ ] The user gives the recording a name and an optional description before starting
- [ ] The user can optionally assign the recording to a module or category (free-text tag, e.g. "Payroll", "Procurement")
- [ ] The launch URL defaults to the client profile base URL but can be overridden for this specific recording
- [ ] The user chooses the browser (Chromium, Firefox, or WebKit) from the configured default or per-recording override
- [ ] The user chooses whether to record video for this session (on / off, with a note that video increases disk usage)
- [ ] The user chooses whether to capture screenshots at each step automatically or only on demand
- [ ] The user can set a recording timeout (defaults to the global setting from Section 2)

### During Recording
- [ ] The browser opens with Playwright codegen mode active so all interactions are captured
- [ ] The dashboard shows a live status panel indicating that recording is in progress
- [ ] The live status panel shows a running count of steps captured so far
- [ ] The live status panel shows elapsed time
- [ ] The user can add a manual annotation / note mid-recording without stopping (this note is saved as a step of type "comment")
- [ ] The user can trigger a manual screenshot at any point during recording from the dashboard (a button that sends a command to the running browser context)
- [ ] Pause and Resume are available so the user can think without generating garbage steps
- [ ] A "Mark Checkpoint" button lets the user flag a specific moment in the recording as a key verification point (used in reports later)
- [ ] The browser window title bar shows "RECORDING IN PROGRESS" so it is never confused with a normal browser session

### Stopping a Recording
- [ ] The user clicks "Stop Recording" in the dashboard
- [ ] The system parses the raw Playwright codegen output into structured step objects (using the existing `engine/parser.py` logic as a starting point)
- [ ] Each step is stored in the database with: step number, action type, selector, input value (if any), URL at time of step, screenshot path (if captured), timestamp, and the raw Playwright line
- [ ] After parsing, the user is taken to a step review screen where they can see every captured step
- [ ] On the review screen, the user can delete any unwanted steps (accidental clicks, wrong navigation)
- [ ] On the review screen, the user can reorder steps via drag-and-drop
- [ ] On the review screen, the user can edit the description / label of any step for cleaner report output
- [ ] On the review screen, the user can mark any step as optional (it will not cause the run to fail if it cannot be completed)
- [ ] On the review screen, the user can add a step manually (type, selector, value)
- [ ] The user saves the recording as a Test in the database, associated with the client profile it was recorded against

## 05 | Multi-Client Test Reuse

This is the architectural core of the platform. A test recorded for one client must be runnable for any other client without modification. Think of it the same way you think about Oracle-delivered content: the object exists once but can be configured for any customer.

### Test Design Rules
- [ ] Tests store steps in generic form. They reference selector patterns, not hardcoded URLs or client-specific text values.
- [ ] Any step value that is client-specific (a company name, an environment hostname, a department code) is stored as a named parameter reference rather than a literal value
- [ ] *Example:* instead of storing `https://acme.fa.us2.oraclecloud.com` in a navigate step, the step stores `{{client.base_url}}/fscmUI/faces/...`
- [ ] The parameter substitution engine resolves `{{client.*}}` tokens at run time using the selected client profile
- [ ] Tests can also reference `{{run.*}}` tokens for values supplied at the time a run is triggered (e.g. a specific employee number to look up)

### Running a Test Against a Different Client
- [ ] The "Run Test" dialog lets the user select any active client profile, regardless of which client the test was originally recorded against
- [ ] The run dialog shows a preview of which parameter tokens will be resolved and what values they will resolve to, before the run starts
- [ ] The run dialog allows the user to override individual parameter values for this run only
- [ ] Run history records which client profile was used, so results from different clients are never confused

### Test Library
- [ ] All saved tests are visible in a searchable, filterable library view
- [ ] Tests can be tagged with modules, categories, and custom labels
- [ ] Tests can be marked as "Master" (canonical, shared across clients) or "Draft" (still being developed)
- [ ] Master tests are protected from accidental deletion (require explicit override)
- [ ] Tests can be cloned to create a client-specific variant if needed
- [ ] Tests can be exported as JSON and imported on another installation of the platform

## 06 | Replay and Run Engine

### Starting a Run
- [ ] Any saved test can be run from the Tests page using a "Run" button
- [ ] The run dialog lets the user select the client profile to run against
- [ ] The run dialog shows any `{{run.*}}` parameters that need to be filled in before the run can start
- [ ] The user can choose whether to record video for this specific run
- [ ] The user can choose headless (no visible browser) or headed (visible browser window) mode
- [ ] The user can choose whether to take a screenshot at every step or only on failures
- [ ] Runs can be scheduled for a future time using a simple date/time picker
- [ ] Multiple tests can be queued into a batch run (runs sequentially, one after another)

### During a Run
- [ ] The Runs page shows live progress: current step number, total steps, current action description, elapsed time
- [ ] The live progress view auto-refreshes without requiring a page reload (use websockets or server-sent events)
- [ ] Each step result (pass / fail / skipped) is written to the database as it completes, not just at the end
- [ ] If a step fails, the platform captures a screenshot of the failure state automatically
- [ ] If a step fails, the platform captures the current page URL and the DOM error message
- [ ] The user can cancel a running run from the UI; cancellation stops the browser cleanly and marks the run as "Cancelled"

### After a Run
- [ ] Run detail page shows every step with its result icon (pass / fail / skip), timestamp, screenshot thumbnail, and any error message
- [ ] Screenshots can be expanded to full size by clicking on the thumbnail
- [ ] Run detail shows total duration, pass rate, and which client profile was used
- [ ] Failed steps show the expected selector and the actual HTML fragment that was found (for debugging)
- [ ] Runs can be re-run from the same Run detail page without going back to the test library
- [ ] Old run data (configurable retention period, default 90 days) is cleaned up automatically by a background job

## 07 | AI-Assisted Test Generation

The AI Studio lets users describe what they want to test in plain language or upload a structured test case file, and the platform turns it into an actual recorded test. This replaces the old manual record-and-label workflow for common scenarios.

> **CRITICAL LOGICAL PROHIBITION:** Do not use the term "browser use" anywhere in the UI or documentation. The capability is described exclusively as "AI-guided recording" or "autonomous test generation".

### Uploading a Test Case File
- [ ] The AI Studio accepts Excel (`.xlsx`), CSV (`.csv`), and plain text (`.txt`) files
- [ ] The file upload control uses the browser's native file picker. The accepted file path is determined by what the user picks -- nothing is hardcoded. There is no configured upload path baked into code.
- [ ] The UI clearly shows the accepted file formats
- [ ] After upload, the platform parses the file and displays a preview table showing the rows it found
- [ ] The user can review and edit any cell in the preview table before sending to the AI
- [ ] The platform handles files with or without a header row (the user toggles this)
- [ ] For Excel files, the platform shows a sheet selector if the file has multiple sheets
- [ ] Files up to 10 MB are supported (configurable max in app settings)

### AI Translation Mode (Fast Path)
- [ ] "Translate to Steps" mode sends the uploaded content to the configured LLM provider and asks it to convert the natural-language rows into structured step JSON
- [ ] The platform uses a well-commented system prompt. The prompt is stored in the database (not hardcoded) so it can be tuned by the user.
- [ ] The response is validated as valid JSON before being stored
- [ ] If the AI returns invalid JSON, the platform retries up to 3 times before showing an error with the raw AI response for the user to diagnose
- [ ] The translated steps are shown on the same review screen as recorded steps (Section 4), allowing the user to edit before saving

### AI Autonomous Recording Mode (Agent Path)
- [ ] "Generate and Record" mode launches a real browser and instructs the AI agent to perform each step autonomously while Playwright records the actual interactions
- [ ] The agent uses the selected client profile for the base URL and credentials
- [ ] The live status panel shows what the AI is currently doing, step by step, in plain English
- [ ] The user can stop the agent at any point from the UI
- [ ] If the agent gets stuck (no progress for a configurable number of seconds, default 30), it pauses and prompts the user with a screenshot asking for guidance
- [ ] Every action the AI takes is logged with a description, the Playwright action that was generated, and a screenshot
- [ ] After the agent finishes, the captured steps go through the same review screen as manual recordings
- [ ] The AI provider, model, and prompt used for the run are stored in the test record for reproducibility

## 08 | Screenshots and Video Recording

### Screenshots
- [ ] Screenshots are saved to the configured output directory, under a subdirectory structure: `output / <client_short_code> / <test_name> / <run_timestamp> / <step_number>.png`
- [ ] The output directory root is never hardcoded. It comes from the app configuration (Section 2).
- [ ] File names include the step number, a sanitized step description slug, and the timestamp
- [ ] Screenshot quality and format are configurable per-run or globally
- [ ] A "Take Screenshot Now" button is available in the live run view to capture an on-demand screenshot
- [ ] Screenshots are displayed as thumbnails in the run detail view with a click-to-expand lightbox
- [ ] All screenshots for a run can be downloaded as a ZIP file from the run detail page

### Video Recording
- [ ] When video is enabled for a run, Playwright's built-in video recording captures the entire session
- [ ] The video file is saved in the same output subdirectory as screenshots
- [ ] Video files are linked from the run detail page and can be played in the browser (use an HTML5 video element) or downloaded
- [ ] The video recording resolution and frame rate are configurable in app settings
- [ ] A video thumbnail (first frame) is generated and shown on the run card in the Runs list
- [ ] Old video files are included in the configurable data retention cleanup job
- [ ] During recording mode, video can also be enabled so the human-performed session is captured alongside the AI-generated steps

## 09 | Reports and Documentation Export

Reports are how consultants deliver evidence of what was tested. They need to look professional and tell the story of the run clearly.

### Excel Report
- [ ] The Excel report is generated using `openpyxl` (already in the repo). Do not replace this dependency.
- [ ] The report filename uses the pattern: `<ClientCode>_<TestName>_<RunTimestamp>.xlsx` -- no path is hardcoded
- [ ] The first sheet is a Summary tab with: client name, test name, run date/time, total steps, pass count, fail count, skip count, overall result (PASS / FAIL), run duration, and consultant initials
- [ ] Each subsequent sheet covers one test module or category (if the test was tagged with modules)
- [ ] Each step row shows: step number, description, action type, expected result, actual result, pass/fail indicator, and an embedded screenshot thumbnail
- [ ] Passed steps use green row shading. Failed steps use red. Skipped steps use yellow.
- [ ] Screenshots are embedded inline in the cell, not as floating images
- [ ] The report includes a cover page with the company logo placeholder (the logo image path is configurable in the client profile)
- [ ] Column widths auto-fit to the content
- [ ] The report is downloadable from the run detail page with a single click

### PDF / HTML Report
- [ ] An HTML report can be generated alongside the Excel report, using the same data
- [ ] The HTML report includes the same sections as Excel but renders screenshots at full resolution in a scrollable page
- [ ] The HTML report can be printed to PDF from the browser, or the platform can generate a PDF server-side (use WeasyPrint or equivalent, do not use headless Chrome for this)
- [ ] Both report types can be generated on demand from the run detail page

### Documentation Package
- [ ] A "Download Documentation Package" button on the run detail page creates a ZIP containing: the Excel report, the HTML report, all screenshots in order, and the video file if one was recorded
- [ ] The ZIP file is named consistently: `<ClientCode>_<TestName>_<RunTimestamp>_docs.zip`

## 13 | What Not to Do

This section is as important as the requirements above. These are explicit prohibitions based on patterns found in the existing codebase.

### These must not appear in the delivered code:
- [ ] No hardcoded URL strings in any Python file other than the first-run bootstrap
- [ ] No hardcoded file paths in any Python file
- [ ] No `.env` file reading in production code paths. The `.env loader` in `core/config.py` is only called during development bootstrap, and a clear code comment marks it as such.
- [ ] No API keys in any configuration file that might be committed to source control
- [ ] No `print()` statements in production code. Use the `logging` module throughout.
- [ ] No bare `except:` clauses anywhere. Always catch specific exception types.
- [ ] No synchronous Playwright calls inside async FastAPI route handlers. Always use `asyncio` or `run_in_executor`.
- [ ] No magic numbers. If a number means something (timeout duration, retry count, max upload size), it has a named constant or config key.
